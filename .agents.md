# Repository agent rules

## Compatibility

- Existing C# scripts are a hard compatibility boundary: preserve public script APIs, directive syntax, core-bot imports, configuration, and normal load/run behavior.
- Rewritten internals must sit behind compatibility facades. Do not require existing scripts to change for runtime, scheduler, cancellation, or diagnostics work.
- Run the legacy-script compatibility corpus before enabling rewritten runtime paths.

## Performance and profiling

- New runtime code must be measured against the Stage 0 monitoring criteria in `docs/script-specs/00-debug-monitoring.md`.
- For performance work, capture before/after CPU, allocations, GC, managed heap, thread-pool state, latency, and working set using the same scenario.
- Keep diagnostics disabled by default. No per-packet logging, raw source/packet capture, unbounded labels, or avoidable hot-path allocations.
- Do not claim an optimization without a representative benchmark or trace and a correctness test.
- Every sampler, timer, task, callback, and trace session must have an owner, cancellation path, bounded lifetime, and observed terminal result.

## Warnings and verification

- New or modified code must introduce no compiler warnings.
- The repository has existing warnings; do not require a zero-warning solution until legacy warnings are reduced.
- For touched projects, compare warning output before/after. Prefer `-warnaserror` for new code or an isolated project when practical.
- Never hide a new warning with a broad suppression. If suppression is unavoidable, keep it narrow and document the reason.
- Verify relevant Debug and Release builds, tests, and compatibility smoke checks before handoff.

## Runtime safety

- Use canonical full paths for runtime identity; keep repository-relative paths for repository metadata.
- Resolve imports relative to the containing file while preserving legacy default-root fallback behavior.
- Keep source discovery, immutable source snapshots, import resolution, compilation, execution, and scheduling as separate stages.
- Use versioned, content-based cache identities. Never cache collectible runtime objects such as `Assembly`, `Type`, delegates, or script instances.
- Do not start a new script generation until the previous generation reports trustworthy `Stopped`, `Failed`, or `Leaked`. A leaked runtime blocks reuse of that client process.
- Capture cancellation tokens per operation; do not read mutable CTS fields from delayed closures.
- Avoid fire-and-forget work. If unavoidable, retain ownership, observe failure, and define shutdown behavior.
- Never put credentials, auth tokens, full script source, or raw packet data in diagnostics, playlists, or IPC logs.

## Scope and collaboration

- Read/search before editing; make the smallest change that satisfies the spec.
- Claim clear file ownership for parallel work. Avoid shared hotspots unless the contract owner has coordinated the change.
- Do not copy VibeSkua wholesale; extract behavior and fit current Avalonia/Core boundaries.
- Preserve unrelated working-tree changes. Do not reset, clean, stage, commit, or push unless explicitly requested.
- Update the relevant script spec when implementation decisions change behavior, compatibility, or acceptance criteria.

## Commits

- When a commit is explicitly requested, use `ArrowDev <dev@jcsawyer.me>`.
- Use one terse, one-line message without a conventional-commit prefix or co-author.
